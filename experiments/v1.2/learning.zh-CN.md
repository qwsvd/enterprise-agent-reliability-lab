# 用一笔退款读懂 Agent 实验

假设客户要求退回 1,499 元。模型读到请求，可以建议查询订单，但它说“已退款”无法改变账户。程序先检查本次允许执行的操作，再通过业务工具读取订单、物流和退款政策。金额达到审批门槛时，数据库只记录等待人工审批。核验程序重新读数据库，看到正确订单、币种、金额和状态后，才允许对外报告等待审批。

A 每轮让模型看已有信息，选择下一批工具或给出结论。第一次查物流失败时，运行循环可以重试允许重试的读取。B 先让模型写出各步骤及其依赖，调度器选择可执行的步骤，执行器调用工具，Reviewer 检查证据。C 在同一张图上增加一条以往任务摘要和一次重新规划机会。工作记忆保存当前任务的证据，经验记忆提供过去的摘要，反思记录哪一步缺了什么，重新规划则需要一次新的模型决定。这里调度、执行、反思记录和安全核验都由普通程序完成。

## 自己验证一次

在仓库根目录打开终端，用 Python 3.11 或更高版本创建虚拟环境。Windows 激活命令为 `.venv\Scripts\activate`，Linux 为 `source .venv/bin/activate`。

```sh
python -m venv .venv
# 激活后执行
python -m pip install -e ".[dev]"
python -m pytest
python -m app.evals.workflow replay experiments/v1.2/live.jsonl
python -m app.evals.workflow_report
```

重放会重新创建数据库，把当时模型写下的决定依次交给执行器。观察六行输出。找出两行 invalid_plan，然后打开 live.jsonl，在对应记录中查看 events 的错误、calls 最后一条 reply 里的 attempts、after 里实际留下的退款。回答三个问题：谁发出了修改建议？谁拒绝了建议？客户的钱最终处于什么状态？能依据字段解释每个回答，才算完成这一步练习。

运行 `python -m app.evals.workflow offline my-fixtures.jsonl` 可以用脚本检验全部 48 种任务与架构组合。输出文件必须是新文件。只有显式执行 `python -m app.evals.workflow live my-pilot.jsonl` 才会使用本机已登录的 Codex CLI 和订阅额度。该命令的上限是 24 次，账户或限额错误会停止本轮。重放和测试均不需要模型账号。

短暂故障的真实试验里，A 最终成功，B 和 C 都把上一步的执行状态写进了新计划，程序拒绝接受。这暴露了接口设计问题。能区分“失败后正确保护数据库”和“完成客户请求”，就能解释这个实验为何有工程价值。系统目前只有一个合成售后业务、小规模固定工具和明确授予的写入范围。对陌生行业、开放目标或长期协作的能力仍需独立实验。

## 面试时如何准确介绍

可以说：“我提出了相同资源上限下比较三种架构的研究问题，Codex 完成了实现、实验和材料编写。公开记录包含六次真实任务运行，包括两个失败样本。”亲自重放、阅读或修改后，再具体介绍自己验证过的数据库字段、看过的失败记录和改动。还没有亲自做过的工作应保留 Codex 署名。
